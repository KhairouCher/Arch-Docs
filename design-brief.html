01What ArchPresent is

ArchPresent is a desktop web platform where architects, architecture students and design offices build print-ready presentations in about 15 minutes, instead of a week in Photoshop.

  • A model is a presentation of several pages (for example a student model of 3 pages, or a full model of 6 or 7). Each page is a Photoshop template that has been converted into a web-editable page.
  • The buyer opens a model in the editor, drops their photos into the zones of each page, edits the text, moves layers, and exports the result at full print resolution. Pages are very large (about 10000 x 7000 px), meant to print at A0.
  • Models are bought with points. Points are topped up by an administrator after the buyer pays the client off the platform. Until a model is bought, every page carries a watermark and cannot be exported.
  • The platform is built for Algeria: the interface is in French (default), Arabic and English, Arabic is laid out right to left, and bundles are priced in dinars (DA).

The one thing it must do well is speed, without losing the quality needed to print at A0. The design should help a buyer finish a presentation quickly and never doubt what is happening to their work.

03What we need from you

  • A visual design for the screens in section 5, in light theme first (it is the main theme), then dark. Each screen in French, English and Arabic (right to left), with the states listed: empty, loading, error, signed out.
  • A brand identity to the extent you think the product needs it: a logo, an accent color and the tone. Today there is only the name and a plain text wordmark.
  • Values for the design tokens (appendix): fill the token table with your colors, type sizes, radii and spacing. The whole app takes its look from these names, so a new design is applied by changing the values, not by redoing every page.
  • Specs for the shared components: buttons (solid, soft, ghost, disabled), form fields, tables, badges, notices, cards, dialogs, tabs and the language switcher.
  • A format we can work from. A Figma file is ideal. Tell us what you prefer.
Not needed: mobile layouts, designer accounts, card payment screens, the AI features planned for later, or the converter (it has no screen). The canvas content itself (the architectural templates) is not part of the interface design.

04Principles and constraints

  • The editor is the product. It is a canvas tool: the page the buyer is working on must get as much room as possible. The interface around it should stay quiet.
  • Trust in the work. The buyer must always see when their work is saved, what will print sharply and what will not, and how much a purchase costs before they press Buy.
  • Everything mirrors in Arabic. Not only the text: the whole layout flips (navigation, panels, arrows, progress bars). The canvas does not flip, because it holds the buyer's design.
  • Long text. French and Arabic strings are usually longer than English. Please test titles, buttons and table headers with the longer languages, and with long model names.
  • Print quality is a hard requirement. The interface must make it clear when a photo is too small to print well at A0 (the editor shows a dpi estimate per photo, in green, orange or red).
  • Light is the main theme. Dark follows the user's system setting. Both are supported by the tokens.
  • Fixed colors for zones. The five zone colors (photo, plan, 3D model, text, logo) are drawn on top of the template art on the canvas and stay the same in both themes.
  • Speed of the interface. The editor redraws a very large canvas on every edit, so avoid effects that cost performance (blurs, large shadows, continuous animation over the canvas).

The editor

The editor is one full-screen screen, not a website page. Today it has:

  • A top bar: the product name, the model title with the page name in brackets ("Sample Model (Cover)"), the draft status ("Draft saved ..."), the language switcher, and the actions Apply, Export PNG and Export JPG.
  • The canvas in the middle, scaled to fit, with a large arrow on each side to move between the pages of the model. The buyer's page is the largest thing on screen.
  • A layers panel on one side, listing only the layers the buyer can edit. A row shows just a colored type badge (photo, plan, 3D model, logo, text) and a name. Selecting a row, or clicking its zone on the canvas, opens its actions: move up or down, fit or fill, upload, remove, the print-quality line for photos, and the text controls (content, font, size, bold, italic, color, alignment) for text. The panel was moved to the side to leave the canvas more room, and rows can be dragged to reorder.
  • Zone labels on the canvas: each empty photo zone shows a colored label ("+ Photo: front"). A selected text shows a box and a resize handle.
  • A watermark tiled across every unpaid page.

06Three languages, right to left

  • French is the default. A switcher (Français, العربية, English) is on every screen, and the choice is remembered.
  • Arabic mirrors the whole layout. Navigation order, side panels, progress bars, back and next arrows and table columns all flip. Please design the Arabic version as its own layout, not only as translated text.
  • Digits are Western (0-9) in all three languages, as used in Algeria.
  • Prices in DA always show with two decimals and no thousands separator: 12000.00 DA. Points show as 20,000 pts and, in Arabic, 20,000 نقطة.
  • Fonts. The interface uses Geist for Latin text. Arabic text uses Cairo. Please propose the interface fonts you want (they must cover Latin and Arabic, and be free to embed). The buyer's own text on the canvas is chosen from seven bundled fonts (Inter, Montserrat, Barlow Condensed, Playfair Display, Cormorant Garamond, Cairo, Amiri) plus Arial; that list is content, not interface.
  • The interface text is in the app's message files and can be sent to you as a table if you want to design with the real wording.

07How the app is styled today

This matters because it decides what a design can ask for and how quickly it can be applied.

  • There is no CSS framework. Every color, size, radius and spacing comes from named design tokens in one file (app/tokens.css), with a light and a dark value for the colors. The Style Ledger page is generated from that file, so the token names and values are always documented.
  • The shared building blocks (buttons, fields, tables, cards, badges, notices) are defined once in app/lib/ui.js, built only from tokens.
  • Page layout is written in the page files themselves. A new design is applied by changing the token values and ui.js, and then adjusting the layout of the pages that differ.
  • Right-to-left works through logical properties (start and end instead of left and right), so a design that is specified with start and end maps directly.
  • Spacing, radii and font sizes come from fixed scales (appendix). A design that uses values outside the scales needs new tokens, which is fine, but please keep the scales small.

08Open design questions

  • Is there a brand (logo, colors) to follow, or do you propose one? None exists yet.
  • The accent color is currently a plain blue. Should it stay, given that five zone colors (blue, green, orange, violet, red) already appear on the canvas and the accent must not be confused with them?
  • How should a model's preview look in the gallery? The real previews will be the first page of the model with the watermark on top.
  • Does the platform need an icon set? There are almost no icons today (arrows and a few marks).
  • How dense should the admin screens be? They are used by two people to work fast.
  • The editor's side panel can be wide or narrow. How much room should the canvas get at 1280 and 1920 px wide?

09Seeing the current app

  • The working app runs on a developer's machine. Ask the developer for a live session or a recorded walkthrough, or run it yourself: install Node.js, then in the web folder run npm install and npm run dev, and open http://localhost:3000.
  • Demo sign-in: any email works. An email starting with admin signs in as an admin, and buyer1@example.com starts with 20,000 points. Everything behind the pages is a placeholder kept in the browser.
  • Editor: open /models and choose "Preview in editor". The sample model has three pages.
  • Project documents (ask the developer to share them): the Plan (what must be built and why), the Blueprint (how each part works), the Style Ledger and the Style Playground (every token and a live page of components), and the Backend Model.

10How we will work

  • The client, an architect, sees and approves the design before it is built, so please plan a discussion with him.
  • The developer applies the approved design, screen by screen, through the tokens and the shared components, and shows each result for review.
  • The launch is planned around mid-February 2027, so the design needs to be settled well before then. Ask the developer for the schedule once the discussion with the client has happened.
